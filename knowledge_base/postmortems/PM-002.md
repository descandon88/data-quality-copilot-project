## Summary

Between 2026-03-19 and 2026-03-23, 1,728 of 115,139 rows in
`bronze.loyalty_transactions` (1.50%) landed with a null `loyalty_id`. The
transactions themselves were otherwise well-formed — real `order_id`, real
`points_earned`, real `transaction_timestamp` — only the join key back to
`loyalty_accounts` was missing, which meant these rows silently dropped out
of every downstream query that joined on `loyalty_id`.

## Impact

- 1,728 transactions became functionally invisible to anything that
  inner-joined `loyalty_transactions` to `loyalty_accounts` — points-balance
  reconciliation, tier-eligibility scoring, and the customer-facing "recent
  activity" feed all silently excluded these rows rather than erroring.
- No error, no failed job, no alert. The pipeline "succeeded" every day this
  was happening — row counts looked normal because nulls still insert fine,
  they just don't join.
- Surfaced only when an analyst doing a manual spot-check on tier-eligibility
  numbers noticed the join-based transaction count was consistently ~1.5%
  lower than the row count in `bronze.loyalty_transactions` directly. Nobody
  was alerted; it was found by someone who happened to compare two numbers
  that should have matched.

## Root cause

The upstream event producer emitting purchase-earn events changed its
payload shape without a version bump or a heads-up to the loyalty-platform
team — a field rename in a client SDK release meant the field the consumer
mapped to `loyalty_id` stopped being populated for a subset of traffic (the
older SDK versions still using the old field name kept working; upgraded
clients silently sent null). The consumer had no schema validation on
inbound events — it mapped whatever fields were present and let anything
missing pass through as null, rather than rejecting the event or flagging
it.

This is the general shape of failure any pipeline hits once it has upstream
producers it doesn't control: a payload contract that isn't actively
enforced isn't really a contract, it's a suggestion, and it will eventually
drift without anyone downstream finding out until a join stops lining up.

## Detection

Manual and very late — a spot-check comparison, not a monitor. Time from
first null row (2026-03-19) to detection (2026-03-23) was four days and
roughly 1,728 rows of silent data loss from every join-dependent view.

## Resolution

1. Identified the affected window by finding the first `transaction_id`
   with a null `loyalty_id` and confirming against event-producer deploy
   logs that it lined up with the SDK release.
2. Backfilled `loyalty_id` for the affected rows by rejoining on `order_id`
   through `olist_orders_dataset` → `olist_customers_dataset` →
   `loyalty_accounts.customer_unique_id`, since `order_id` was never null
   and uniquely resolves to exactly one `loyalty_id`.
3. Added inbound payload validation at the consumer: `loyalty_id` (and
   `order_id`) are now required, non-null fields — an event missing either
   is routed to a dead-letter table instead of being written with a null
   join key, so a future drift fails loudly instead of silently.

## Follow-up: validation rule added

See `knowledge_base/rules/RULE-002.md`. A daily check now flags any row in
`bronze.loyalty_transactions` with a null `loyalty_id`. This is warn-and-continue,
not hard-stop — see RULE-002 for the reasoning on why this incident class
gets a different enforcement level than PM-001's.

## Lessons learned

- A pipeline that "succeeds" every day is not the same thing as a pipeline
  that's correct every day. Row-count and job-status monitoring alone would
  never have caught this — nothing failed.
- Null join keys are a class of bug that's invisible at write time and only
  visible at join time, which means the earliest place to catch it is
  validating the write, not auditing the read.
- An upstream contract you don't control (an event producer's payload
  shape) still needs local enforcement on your side. Trusting the producer
  not to change silently is not a strategy.
