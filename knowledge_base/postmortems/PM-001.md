## Summary

Between 2026-03-04 and 2026-03-10, the loyalty events consumer double-credited
points on a subset of purchase-earn events, inflating customer point balances.
796 of ~115,139 transactions in `raw.loyalty_transactions` (0.69%) were
duplicate `earn` rows — same `loyalty_id`, same `order_id`, same
`points_earned` value, generated seconds apart by two deliveries of the same
underlying event.

## Impact

- 796 duplicate `earn` transactions, concentrated on a subset of `loyalty_id`s
  rather than spread evenly, consistent with retries clustering around a
  specific consumer-restart window rather than random noise.
- Downstream effect: `raw.loyalty_accounts.points_balance` for affected
  accounts was overstated. No customer-facing redemption was blocked by this
  (balances were too high, not too low), but it created a real liability —
  customers could redeem points that were never legitimately earned.
- Nothing caught this at write time. It surfaced during a routine weekly
  reconciliation between `SUM(points_earned)` in `raw.loyalty_transactions`
  and the order count in `raw.olist_order_items_dataset` for the same date
  range — the two didn't tie out.

## Root cause

The events consumer that writes `earn` rows into `raw.loyalty_transactions`
does not have an idempotency key. Each purchase event should produce exactly
one `earn` row per `order_id`, but the consumer's at-least-once delivery
guarantee means a redelivered message (consumer restart, brief downstream
timeout, rebalance) produces a second `earn` row with a new `transaction_id`
but the same `order_id` and `loyalty_id`. There was no uniqueness constraint
or dedup step to catch it — inserts were pure appends.

This is the same shape of failure Ibotta documented publicly: financial or
balance-affecting writes that aren't idempotent will eventually double-write,
because "redeliver on uncertainty" is the correct behavior for the messaging
layer and the correct behavior for the consumer is to make redelivery safe,
not to assume it won't happen.

## Detection

Manual, and late — a weekly reconciliation query, not an automated check.
Time from first duplicate (2026-03-04) to detection (2026-03-10) was six days
and roughly 115k transactions of exposure.

## Resolution

1. Backfill: identified duplicate pairs via
   `(loyalty_id, order_id, transaction_type = 'earn')` having `COUNT(*) > 1`,
   kept the earliest `transaction_id` by `transaction_timestamp`, reversed the
   rest with an explicit `adjustment` transaction (not a silent delete —
   `raw.loyalty_transactions` is meant to be an append-only ledger, so the
   correction has to be a new row, not a mutation of history).
2. Recomputed `points_balance` in `raw.loyalty_accounts` for every affected
   `loyalty_id` from the corrected transaction history.
3. Added `transaction_id` as a deterministic hash of
   `(order_id, transaction_type, points_earned)` at write time, so a
   redelivered event produces the same `transaction_id` and can be upserted
   instead of appended — this is the actual fix, not the backfill.

## Follow-up: validation rule added

See `knowledge_base/rules/RULE-001.md`. A daily check
now flags any `(loyalty_id, order_id)` pair with more than one `earn` row
within a 24-hour window — this is a hard-stop check on the ingestion job, not
a warning, because the cost of a silent duplicate (real financial exposure)
outweighs the cost of a delayed load.

## Lessons learned

- Append-only event tables need idempotent write keys from day one. Retrofitting
  one after 115k rows exist is possible but expensive — the backfill logic has
  to reconstruct "what should have happened" from ambiguous duplicate data.
- A reconciliation query that runs weekly is a smoke detector with a six-day
  delay. The same check needs to run inline with ingestion, not as an
  after-the-fact audit.
- Whether this class of error should hard-stop the pipeline or just warn
  depends on what's on the other side of the write. Point balances are a
  liability — get this one wrong and you're honoring redemptions that were
  never earned. That argues for hard-stop, not warn.
