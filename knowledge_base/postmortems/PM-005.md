## Summary

3,879 of 9,698 accounts marked `tier = 'gold'` in `bronze.loyalty_accounts`
(40%) have a `last_activity_date` more than a year old. Gold tier carries
real operating cost — free expedited shipping, priority support queueing,
bonus-earn multipliers — and 40% of the accounts currently receiving that
cost had gone effectively inactive well before this was noticed.

## Impact

- 3,879 inactive accounts continued receiving gold-tier perks with no
  offsetting engagement — a direct, ongoing cost leak, distinct from
  PM-001/PM-004's transactional financial exposure but a real line-item
  cost nonetheless (subsidized shipping and support capacity spent on
  customers who'd stopped purchasing).
- Because tier is also read by marketing segmentation, 3,879 inactive
  customers were included in gold-tier-targeted campaigns (higher-cost
  channels, gold-exclusive offers) based on a status that no longer
  reflected real behavior.
- No error at any layer. The nightly tier-reassessment job's scheduler
  entry showed "success" every run — it just stopped doing the reassessment
  logic partway through a deploy and nobody validated its output against
  expected row-touch counts.

## Root cause

The nightly job that downgrades accounts whose `last_activity_date` has
aged past the gold-retention window silently stopped executing its
core reassessment query after a deploy changed an upstream dependency's
output schema in a way the job's query no longer matched — the query
returned zero rows to update instead of erroring, and the job's own
success/failure signal was based on "did the job process complete,"
not "did the reassessment actually touch the rows it should have." A job
that completes without error but processes nothing "succeeds" by every
signal anyone was watching.

## Detection

Manual — found during the same broader account-health audit that surfaced
PM-004, when tier distribution was cross-checked against activity recency
and the mismatch was large enough to be obvious once someone looked. Like
PM-003 and PM-004, this is an accumulated condition, not a single dated
event — the job had been silently no-op'ing for an unknown period before
the audit, not just since one specific date.

## Resolution

1. Quantified: joined `tier = 'gold'` accounts against
   `last_activity_date`, counted those older than the retention window
   (1 year) — 3,879 rows.
2. Ran a corrected, one-time reassessment pass to downgrade the genuinely
   stale accounts, rather than waiting for the next scheduled run (which
   was still broken).
3. Fixed the job's query to match the upstream schema change.
4. Changed the job's success criteria from "process exited zero" to
   "process exited zero AND touched a row count within an expected
   range for the account base size" — a reassessment job that updates
   zero rows against tens of thousands of eligible accounts should now
   fail loudly instead of reporting success.

## Follow-up: validation rule added

See `knowledge_base/rules/RULE-005.md`. A daily check flags gold-tier
accounts whose `last_activity_date` has aged past the retention window.
Warn-and-continue, not hard-stop — see RULE-005 for why.

## Lessons learned

- "The job ran without error" and "the job did what it was supposed to do"
  are different claims, and monitoring only the first one misses an entire
  class of silent failure — a query that matches nothing is not the same
  as a query that fails.
- Batch jobs that mutate state based on a condition (age out, reassess,
  expire) should validate their own blast radius against a sanity range,
  not just their own exit code. Zero rows touched against a population
  where some nonzero number should always be eligible is itself a signal.
- Not every incident here is a financial-ledger problem like PM-001/PM-004.
  A cost leak from over-granted perks is still worth a hard number and a
  rule, even though the enforcement response is different (see RULE-005).
