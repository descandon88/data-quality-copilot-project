## Summary

480 of 96,096 accounts in `bronze.loyalty_accounts` (0.50%) show a negative
`points_balance` — as low as -300 points. A negative balance means the
account redeemed more points than it ever had: the platform honored
redemptions it should have rejected.

## Impact

- 480 accounts with a negative balance, representing redemptions that
  exceeded the customer's actual earned points at the time of redemption —
  real financial exposure, the same category of liability as PM-001, just
  triggered by a different mechanism (a redemption race, not a duplicate
  earn).
- Unlike PM-001, this wasn't caught by a reconciliation query that compares
  two aggregates — a negative balance is directly visible in a single-table
  scan (`points_balance < 0`), which makes it more surprising that it went
  unnoticed as long as it did. There was simply no check running that
  scan.
- No customer-facing error occurred — redemptions succeeded, which is
  exactly the problem. From the customer's perspective nothing looked
  wrong.

## Root cause

The redemption path read `points_balance`, checked it against the
requested redemption amount, and wrote the decremented balance back — three
separate steps with no locking or atomic compare-and-set between them. Two
redemption requests for the same account arriving close together could
both read the same (sufficient) balance, both pass the check independently,
and both write a decrement — the second write landing after the first,
based on a balance that was already stale. Neither request was wrong in
isolation; the bug is that "read balance, check, write" isn't a single
atomic operation, so two concurrent instances of it can both succeed when
only one should have.

This is a standard check-then-act race condition, the kind that's invisible
under normal load and only shows up when a customer (or a script, or a
retried client request) fires two redemptions close enough together to
land in the same race window.

## Detection

Manual — found by the same broader join-key/integrity audit that surfaced
PM-003, when `points_balance < 0` was added as one more sweep. Like PM-003,
there's no clean single incident date; this is an accumulated rate, not a
dated event with a start and end.

## Resolution

1. Quantified: `select * from loyalty_accounts where points_balance < 0` —
   480 rows.
2. For each affected account, reconstructed the correct balance from the
   full transaction history in `loyalty_transactions` (sum of
   `points_earned` minus sum of `points_redeemed`) rather than trusting the
   stored `points_balance`, since the stored value was the thing that had
   drifted.
3. Corrected `points_balance` to the reconstructed value. Where the
   reconstructed value was still negative (meaning the redemption really
   did exceed legitimately earned points, not just a display artifact of
   the race), flagged the account for manual review rather than silently
   zeroing it out — a negative true balance is a customer-support and
   possibly fraud question, not something to paper over automatically.
4. Fixed the redemption path to use an atomic
   `UPDATE ... SET points_balance = points_balance - :amount WHERE
   loyalty_id = :id AND points_balance >= :amount` (single statement,
   database-enforced check-and-decrement) instead of separate read-check-write
   steps, closing the race at the source.

## Follow-up: validation rule added

See `knowledge_base/rules/RULE-004.md`. A daily check now flags any account
with `points_balance < 0`. Hard-stop, not warn — see RULE-004 for why this
gets the same enforcement level as RULE-001.

## Lessons learned

- "Read, check, write" is never atomic unless you make it atomic. Any
  balance-affecting operation needs either a database-level atomic
  operation or an explicit lock — application-level sequencing is not
  enough once there's any concurrency at all.
- A negative balance is a directly-visible violation (one column, one
  comparison) — this class of bug doesn't need a clever reconciliation
  query the way PM-001 did, it needs someone to actually run the trivial
  check. The gap here wasn't detection difficulty, it was that no scheduled
  check existed at all.
- Financial-liability checks (this, RULE-001) get hard-stop enforcement.
  Data-completeness checks (RULE-002, RULE-003) get warn-and-continue. The
  dividing line isn't "how bad does this look," it's "can honoring this bad
  data cost real money before anyone notices."
