## Summary

345 of 115,139 rows in `bronze.loyalty_transactions` (0.30%) reference a
`loyalty_id` that does not exist in `bronze.loyalty_accounts`. These
transactions are not corrupt — they carry real `order_id`s, real
`points_earned` values, real timestamps — but the account they claim to
belong to was never created, or was created after the transaction landed.

## Impact

- 345 orphaned transactions could not be attributed to any account: any
  query joining `loyalty_transactions` to `loyalty_accounts` (inner join)
  silently dropped them, same failure shape as PM-002 but with a different
  root cause — here the account row is genuinely missing, not just
  unjoinable due to a null key.
- Point totals computed from `loyalty_transactions` alone (without the join)
  overcounted relative to what `loyalty_accounts.points_balance` could
  actually attribute to a real customer — 345 transactions' worth of points
  existed nowhere a customer could claim them.
- No hard failure. The ingestion job for both tables succeeded independently
  every run; nothing enforced that a transaction's `loyalty_id` had to
  already exist in the accounts table at write time.

## Root cause

`loyalty_accounts` and `loyalty_transactions` are populated by two
separate write paths — account creation happens on enrollment, transaction
writes happen on purchase — and there is no ordering guarantee between
them. A customer who enrolls and makes a purchase in the same session can
have their purchase-earn event processed by the transactions consumer
*before* the enrollment consumer finishes committing the new account row,
if the account-creation path is even slightly slower (a retry, a brief
downstream lock, ordinary queueing delay under load). The transaction
lands referencing a `loyalty_id` that is valid and will exist momentarily,
but doesn't exist yet at the instant the transaction consumer commits.

This is the classic late-arriving-dimension problem: a fact row can
legitimately arrive before its dimension row when the two are written by
independent, unsynchronized processes, and any pipeline that assumes
dimension-before-fact ordering without enforcing it will eventually see
this class of race.

## Detection

Manual — an ad hoc referential-integrity audit run after PM-002 prompted a
broader look at join-key health across the loyalty tables, not a scheduled
check. There is no reliable "time to detection" for this one, since the
orphaned rows accumulate gradually rather than in one incident window —
unlike PM-001 and PM-002, this isn't a single dated event, it's an ongoing
low rate of races that had never been measured until this audit.

## Resolution

1. Quantified the problem: `left join` from `loyalty_transactions` to
   `loyalty_accounts` on `loyalty_id`, counted rows where the account side
   was null — 345 rows.
2. For orphaned rows where the referenced `loyalty_id` existed by the time
   of the audit (the account had since landed, just after the transaction),
   no data was lost — these self-healed once both writes committed, and the
   join failure was transient at read time only if queried in the race
   window. For rows where the `loyalty_id` still did not exist at audit
   time (a true orphan, no matching account ever created), the transaction
   was routed to a quarantine table pending manual investigation rather
   than silently dropped or auto-attributed to a guessed account.
3. Longer-term fix: the transactions consumer now checks for the account's
   existence before committing a transaction row; if the account isn't
   found, the event is retried with backoff for a bounded window (covering
   ordinary write-path latency) before quarantining, rather than writing
   an orphaned reference immediately.

## Follow-up: validation rule added

See `knowledge_base/rules/RULE-003.md`. A daily check flags any
`loyalty_transactions` row whose `loyalty_id` has no matching row in
`loyalty_accounts`. Warn-and-continue, not hard-stop — see RULE-003 for
why.

## Lessons learned

- Two tables written by independent processes need an explicit ordering
  guarantee or an explicit tolerance for out-of-order arrival — assuming
  one implicitly is how this class of bug gets introduced.
- Late-arriving-dimension races are usually not visible as a discrete
  incident with a clean start/end date the way PM-001 and PM-002 were —
  they're a background rate that just sits there until someone measures it.
  That argues for a recurring automated check over a one-time audit, since
  a one-time audit only tells you the rate on the day you ran it.
- Not every orphan is a bug in progress — some self-heal once the slower
  write path catches up. The quarantine-and-review step exists specifically
  to distinguish "will resolve itself" from "will never resolve" before
  treating either one as ground truth.
